# コンテナ・クラウド誤設定プレイブック

Docker/Kubernetes/クラウド環境が対象に含まれる場合の定番の誤設定パターン。設定ミス起因が大半で、複雑な脆弱性を突くより発見・実証が速いことが多い。

## Docker
- **Dockerソケットの露出**: `/var/run/docker.sock` がコンテナ内から読み書きできる、またはTCP経由(2375/tcp、認証なしが多い)で公開されていると、ホスト上で任意のコンテナを起動できてしまい、事実上ホストの制圧に直結する
  - 確認: `docker -H tcp://<target>:2375 ps` が通るか
  - 悪用: ホストのファイルシステムをマウントした特権コンテナを起動すれば、ホスト側に任意のファイル読み書きが可能
- **特権コンテナ(`--privileged`)**: コンテナ内からホストのデバイス・カーネル機能に直接アクセスでき、コンテナエスケープの糸口になる
- コンテナ内に残された `.env` / 設定ファイル / SSH鍵などの機密情報の探索も基本
- イメージのビルド履歴(`docker history <image>`)に認証情報が焼き込まれていないか確認

## Kubernetes
- **kubelet APIの認証なし公開**(10250/tcp): 認証・認可が不十分だとPod一覧取得やコマンド実行が可能なことがある
- **kube-apiserverの匿名アクセス**: `kubectl --server=https://<target>:6443 get pods` が認証なしで通らないか
- **過剰権限のService Account**: Pod内から利用可能なService Accountトークンが、想定以上の権限(他Namespaceの読み取り、Secret閲覧等)を持っていないか確認
- Podのメタデータ(`/var/run/secrets/kubernetes.io/serviceaccount/token`)は侵害したコンテナ内から読める前提で扱う

## クラウド(AWS/GCP/Azure等)のメタデータエンドポイント
- クラウドインスタンス上で動くアプリがSSRF脆弱性を持つ場合、インスタンスメタデータエンドポイント(AWSなら `http://169.254.169.254/latest/meta-data/`)経由で一時認証情報を窃取できることがある
- IMDSv2(トークン必須)が強制されていない環境では特に成功しやすい古典的な攻撃パターン

## 秘密情報の露出
- 公開リポジトリ・ビルド成果物・`.git`ディレクトリの露出(`curl http://<target>/.git/config`)からAPIキー・認証情報が漏れていないか
- `.env`、`config.yml`、バックアップファイル(`.bak`, `.old`)がWeb経由で直接ダウンロードできないか確認
- クラウドストレージ(S3バケット等)の公開範囲設定ミスで内部データが読み書き可能になっていないか

## 報告
- 誤設定を発見した段階で report(recon または exploit)
- 実際にホスト権限やクラウド認証情報の取得に成功したら report(finding, severity="critical")(横展開の起点になりやすいため高severityになりやすい)
