# Web応用脆弱性プレイブック

02_web_exploitation.md(SQLi/XSS/認証まわり)より踏み込んだ、現代的なWebアプリでよく見つかるクラス。

## SSRF(Server-Side Request Forgery)
1. URLを入力として受け取る機能(画像取得、Webhook、PDF生成、外部連携)を探す
2. `http://169.254.169.254/`(クラウドのメタデータエンドポイント)や `http://localhost:<内部ポート>` を指定し、サーバー側が内部リソースにアクセスしてしまわないか確認
3. 成功すればクラウド認証情報の窃取や、外部から直接到達できない内部サービスへのアクセスに繋がる(container/cloud misconfigのメタデータ窃取と直結)

## XXE(XML External Entity)
1. XMLを受け付けるエンドポイント(SOAP API、ファイルアップロードでXML系フォーマットを扱うもの)を探す
2. 外部エンティティ定義(`<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>`)を含むXMLを送り、ローカルファイルの内容がレスポンスに反映されないか確認
3. Out-of-band(外部への通信を発生させて確認する)手法も併用できる

## 安全でないデシリアライズ(Insecure Deserialization)
1. Cookie・パラメータにシリアライズされたオブジェクト(Java, PHP, Pythonのpickle等)が使われていないか確認
2. シリアライズ形式が特定できたら、既知のガジェットチェーン(言語・フレームワークごとに研究されている)を使ったRCEの可能性を検討
3. 汎用的に危険度が高いクラスなので、確認できただけでも高severityで報告してよい

## JWT(JSON Web Token)の不備
- **alg=none攻撃**: 署名アルゴリズムを`none`に変更して署名検証自体をバイパスできないか
- **署名鍵の弱さ**: HMAC系(HS256等)の場合、秘密鍵が推測可能・総当たり可能な弱い値になっていないか
- **公開鍵/秘密鍵の混同**: RS256からHS256への変更で、公開されている公開鍵を秘密鍵として使わせる攻撃が成立しないか
- **有効期限・失効の不備**: 期限切れ・ログアウト後のトークンがまだ有効なままになっていないか

## SSTI(Server-Side Template Injection)
1. 入力値がテンプレートエンジンに直接渡されている疑いがある箇所(エラーメッセージにテンプレート構文が反映される等)を探す
2. `{{7*7}}` や `${7*7}` のようなペイロードを入れ、`49`のように評価された結果が返ってくるか確認(テンプレートエンジンの種類によって構文が異なる)
3. 評価されることが確認できたら、使用しているテンプレートエンジン特有のRCEチェーンを検討

## コマンドインジェクション
1. OSコマンドを内部で実行していそうな機能(ping機能、ファイル変換、画像処理等)を探す
2. `; id` `| id` `` `id` `` `$(id)` などのメタ文字を挿入し、コマンドが実行されないか確認
3. フィルタがある場合はバイパス手法(引用符の混在、改行、エンコーディング)を検討

## GraphQL / API特有の観点
- **イントロスペクションの有効化**: `__schema`クエリでAPI全体の構造(意図せず公開されているフィールド含む)を取得できないか
- **過剰な情報取得(オーバーフェッチ)**: 1回のクエリで想定以上の関連データ(他ユーザーの情報等)まで取得できないか
- **レート制限の不備**: 総当たり・大量列挙がAPIレベルで制限されていないか

## 報告
- 「試行中」はreport(exploit, "...")、確定した脆弱性はreport(finding, severity=...)
- SSRFはクラウド環境なら特に高severity(認証情報窃取に繋がるため)
